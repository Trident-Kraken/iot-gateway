# 架构与设计权衡 — iot-gateway

> 围绕线程模型、I/O 多路复用、自定义二进制协议、对象池与并发同步等核心设计决策的技术权衡说明。

---

### 1. 为什么采用 epoll ET 而不是 LT？

LT（水平触发）模式下只要 fd 仍有未读数据，每次 `epoll_wait` 都会持续通知，容错度高但多余的系统调用往返会增加调度开销。ET（边缘触发）仅在 fd 从不可读变为可读时通知一次，配合 `while` 循环一次性排空接收缓冲区直到 `EAGAIN`。

对于高并发长连接网关，ET 模式减少了重复唤醒和无效的 `epoll_wait` 往返，代价是代码必须严格遵循“循环读取至 `EAGAIN`”的约束，否则残留字节会导致后续事件饥饿。

---

### 2. 为什么 ET 模式下必须循环 recv 至 EAGAIN？

ET 仅在状态跳变沿通知一次。若内核接收缓冲区到达 4KB 数据而应用层只读走 1KB，剩余 3KB 由于 fd 仍处于“可读”稳态而不会触发下一次 `epoll_wait` 通知，直到对端继续发送新数据产生新边沿为止。

`for (;;)` 循环调用 `recv()` 直至返回 `-1` 且 `errno == EAGAIN/EWOULDBLOCK`，可确保内核缓冲区完全排空，为下一次状态跳变做好准备。

---

### 3. RingBuffer 为何按连接独立而非全局共享？

TCP 是无边界字节流，多连接数据并发到达时帧边界可能交叉打散。若所有连接共享同一 RingBuffer，连接 A 的帧头 `0xAA` 之后可能紧随连接 B 的 Payload 字节，直接破坏帧结构。

每连接独立的 RingBuffer 是“per-connection parser context”的前提：每个连接维护各自的状态机状态、偏移与环形存储，彼此完全隔离。对于数百至上千路长连接场景，4KB/连接的内存开销可控且无需加锁（SPSC 单线程读写）。

### 4. 粘包/拆包状态机如何流转？

```
                  ┌──────────┐
                  │WAIT_HEAD │ ← 初始状态
                  │ 找 AA 55 │
                  └────┬─────┘
                       │ 读到 AA 55
                       ▼
                  ┌──────────┐
                  │WAIT_LEN  │
                  │ 读 2B 长度│
                  └────┬─────┘
                       │ 读到 payload_len
                       ▼
                  ┌──────────┐
                  │WAIT_     │
                  │PAYLOAD   │ ← 读 cmd + N 字节
                  └────┬─────┘
                       │ 读完 payload_len 字节
                       ▼
                  ┌──────────┐
                  │WAIT_CRC  │
                  │ 读 2B CRC│
                  └────┬─────┘
                       │ CRC 校验通过
                       ▼
                  ┌──────────┐
                  │FRAME_    │
                  │COMPLETE  │ → 回调 → 立即回到 WAIT_HEAD
                  └──────────┘
```

三种网络边界场景均在同一状态机内自然处理：
1. **整帧到达**：依次流转至 `FRAME_COMPLETE`，回调递送后回到 `WAIT_HEAD`；
2. **半帧拆包**：字节不足时停留在当前状态，保留已读取的 `temp_buf` 与 `recv_offset`，等待下次 `recv` 继续消费；
3. **多帧粘包**：当前帧完成后立即重置，继续消费同一 RingBuffer 中剩余字节。

### 5. 线程池条件变量为何用 while 而非 if？

POSIX 规范允许 `pthread_cond_wait()` 发生虚假唤醒（spurious wakeup）；同时在多工作线程竞争场景下，单次信号可能唤醒多个等待者，先抢到互斥锁的线程消费完唯一任务后，其余唤醒线程面对的是空队列。

使用 `while (g_head == NULL && !g_shutdown)` 在重新获取互斥锁后再次校验条件，可避免空队列继续执行导致 `NULL` 指针解引用。

### 6. 心跳线程、工作线程与 I/O 线程如何同步？资源如何安全回收？

心跳线程通过 `conn_manager_foreach` 遍历连接链表，采用**两段式模式**：持有 `conn_manager` 互斥锁期间仅将超时连接的 `(fd, generation)` 收集到局部数组，解锁后不直接 `close(fd)`，而是经 `epoll_worker_request_close()` 写入 self-pipe，将关闭动作串行化到 epoll 线程。

若由心跳线程直接 `close(fd)`，会与 epoll 线程正在进行的 `recv()` / `epoll_ctl()` 产生竞态，甚至在内核复用该 fd 后误关新连接。引入 `fd + generation` 双重匹配与 self-pipe 后，连接关闭链路统一收敛至 epoll 线程：

`connection_close()` → `epoll_ctl(DEL)` → `packet_parser_unregister()` → `conn_manager_remove()` → `close(fd)` → 挂入垃圾链批末归还连接对象池。

并发边界防护：`epoll_wait` 返回的 `events[]` 是事件快照，同批内先处理的 pipe 关闭消息可能已关闭某连接，而该连接的残留事件仍位于 `events[]` 后续位置。通过 `connection.closed` 标志阻断重入，同时关闭的槽位先入 `g_conn_trash` 链、**批末**统一归还对象池，确保批内槽位不被 `accept()` 复用，从而彻底消除双重释放与空闲链自环。

### 7. 为什么选择 `0xAA 0x55` 作为帧头并统一大端字节序？

`0xAA`（`10101010`）与 `0x55`（`01010101`）为互补比特模式，在常见 ASCII 文本与零值填充中连续出现的概率较低（随机双字节碰撞概率 1/65536），适合状态机在 `WAIT_HEAD` 阶段逐字节滑动自同步。

多字节数值字段（2 字节 Payload 长度与 2 字节 CRC16）统一采用网络字节序（big-endian），在编解码边界显式使用 `htons`/`ntohs` 转换，保证跨主机架构传输一致性。

### 8. 压测吞吐受限时如何自底向上排查定位？

性能瓶颈通常按自底向上的分层顺序定位：

1. **系统与 CPU 分布**：通过 `htop` / `top -H` 观察 I/O 线程与工作线程 CPU 占用比例；用 `ss -tn` 查看内核 `Recv-Q` / `Send-Q` 是否堆积。
2. **I/O 层事件循环**：检查 ET 模式下 `recv()` 是否循环排空至 `EAGAIN`，是否存在多余的 `LOG_INFO` 磁盘刷盘争抢 `g_log_mutex`。
3. **任务队列水位**：统计 `task_queue_push` 与 `task_queue_pop` 的队列深度及 `ENOMEM` 拒入次数，确认消费者线程池是否成为瓶颈。
4. **MQTT 上报路径**：核对 `mqtt_qos` 配置（QoS 1/2 在高并发下的 PUBACK/PUBCOMP 开销）以及离线缓存命中率。
5. **热点剖析**：使用 `perf top` 定位高耗时热点函数（如字符串解析、格式化拷贝与内存分配抖动）。

### 9. 为什么采用函数指针数组做命令分发而非 `switch-case`？

原因有两点：**确定性 O(1) 查找**与**解耦扩展**：

1. 当命令字空间稀疏时（如 `0x01`、`0x7F`、`0xFE`），`switch-case` 容易退化为线性比较链；`g_cmd_handlers[256]` 以 `uint8_t` 命令字直接数组索引，与 `uint8_t` 值域天然对齐，无需边界判断。
2. 新增业务命令只需实现新 handler 并在 `cmd_handlers_init()` 增加一行注册映射，无需修改 `worker_process_task()` 分发主干，降低并发开发与合并冲突风险。

### 10. 传感器上报为何默认选择 MQTT QoS 0，何时需要 QoS 1/2？

QoS 级别选择取决于业务对单条采样丢失的容忍度与延迟预算：

- **QoS 0（默认）**：传感器周期性采集温湿度（每秒 1~10 条）对单点丢失容忍度较高，fire-and-forget 无需等待 PUBACK，延迟最低且对 broker 内存压力最小。
- **QoS 1 / QoS 2**：网关通过 `config/gateway.ini` 的 `mqtt_qos` 同样支持 QoS 1 与 QoS 2，由 `mosquitto_loop()` 的 inflight 状态机与 `on_publish` 回调处理确认与重传，适用于告警通知或关键控制状态同步等高可靠场景。

---

### 11. 为什么网关不引入进程级全局状态机？

网关生命周期呈现“线性启动 + 模块自治”特征，而非多状态交叉迁移的事件驱动系统：

- **启动期**：`main()` 按配置校验 → 日志/信号 → 命令表 → MQTT → 线程池 → epoll 管道 → 心跳 → 监听 socket 顺序线性初始化，任一步失败即严格逆序清理并 fail-fast 退出。
- **运行期**：状态迁移天然收敛在各自职责边界内——协议层维护五态拆包状态机、`mqtt_client` 维护断线重连与离线缓存自治循环、`epoll_worker` 维护连接代际与批末回收生命周期。将状态机留在真正存在状态迁移的模块内部，可避免冗余的全局状态同步复杂度。
